# Compiler-cache trial on compute01, 2026-11-27

[J1306, issue #608](https://git.kayg.org/kayg/infraternal/issues/608)

## Recommendation

Keep kache 2.4.0 out of shared build-host gates. The cold wrapped x86_64
musl build failed in vendored OpenSSL, so it produced no binary for the
required SHA-256 comparison. This is a compatibility result. The failed
run cannot establish a build speedup or estimate warm cross-worktree reuse.

If another evaluation is warranted, first verify that the native compiler
query reaches the pinned Zig driver. Qualify both static hashes and the
workspace test outcomes with fresh targets. Then compare warm builds
against the existing sccache configuration. Keep any pilot in one trusted
build domain with a private cache, socket and XDG cache root. A colocated
store on the build filesystem would be a separate disk-footprint
experiment. [J1306 evidence](https://git.kayg.org/kayg/infraternal/issues/608#issuecomment-106977)

## Scope

The trial started with the gate's exact static build commands in the pinned
`nix develop` shell. The test and warm cases were conditional on matching
static outputs. Both controls and the wrapped build used ordinary Cargo and
the repository's compiler drivers. The private install used the locked
kache 2.4.0 crate. The wrapped run set `RUSTC_WRAPPER` directly and skipped
the upstream shim setup. Compute01 ran each build serially through
`build-slot`, with four Cargo jobs. The prepared workspace test command
used a loopback-only namespace and a private test-state directory.

Each build got a fresh Cargo target on `/mnt/build`. The worktrees pinned
`a9de45fc1a1c28b1753edfa22edfbe411f6a7af0` and
`4b88aee0edc6a3ddc7756d414ca8742a948a0726`, four first-parent revisions
apart. The third worktree used the latter revision with a private comment
added to `crates/infraternal-link/src/lib.rs`. Cargo incremental compilation
and kache target and incremental seeding were disabled. The wrapped build
started with an empty compiler store on the home filesystem and an 8 GiB
blob budget. The toolchain and dependency downloads could already be warm.

The correctness check required matching SHA-256 at each shipping
architecture and matching outcomes for the workspace tests. Wall and child
CPU seconds came from Bash's `time`, with separate accounting for the
private daemon. Thirty-second disk samples measured allocated bytes using
one `du` invocation across the target and cache. The peak samples are
lower bounds. Load averages describe the shared VM.

## Why the build stopped

The pinned `cc` 1.11.3 adds a recognized `RUSTC_WRAPPER` named `kache` to
the native compiler command. The logged OpenSSL configuration therefore
used `CC="…/kache …/.cargo/musl-cc-avx512.sh"` even though the trial only
set the Rust wrapper variable. The project's shell driver delegates to its
pinned Zig C compiler. [Pinned cc environment documentation](https://docs.rs/cc/1.11.3/cc/#external-configuration-via-environment-variables)

The direct driver printed `clang version 22.1.8` and exited 0. The same
`--version` argument through kache produced an unrecognized-subcommand
error for the shell driver and exited 2. OpenSSL's x86_64 assembly translator
checks for GNU assembler or a Clang version before selecting its quoted
ELF section syntax. Both generated AES assembly files contained the
fallback `.section .note.gnu.property, #alloc`, which Zig rejected with
`error: expected string`. This demonstrates a compiler-query compatibility
failure with this invocation. The trial reached no wrapped artifact hash.
[OpenSSL translator](https://github.com/openssl/openssl/blob/master/crypto/perlasm/x86_64-xlate.pl),
[local compiler-query output and build log](https://git.kayg.org/kayg/infraternal/issues/608#issuecomment-106977)

## Filesystem and sharing

At preflight compute01 reported 56 GiB available on the 591 GiB ext4 home
filesystem (91% used) and 960 GiB available on the 984 GiB ext4 build
filesystem. These are separate devices, so a home-to-target restore copies
bytes. Same-filesystem placement is a prerequisite for hardlinks. Upstream
also distinguishes libraries eligible for hardlinks from mutable executables
and loadable outputs, which use clone or copy. A bounded blob budget and
actual filesystem headroom are separate measurements.
[Upstream deduplication](https://ninja.kunobi.com/docs/kache/deduplication), [upstream storage accounting](https://ninja.kunobi.com/docs/kache/getting-started/storage)

The private run needs an explicit `XDG_CACHE_HOME` as well as a private
`KACHE_CACHE_DIR` and runtime directory. The first daemon started in the
correct private runtime but wrote its diagnostic log to the default XDG
cache root. I stopped that attempt, moved its log into the private evidence
directory, and restarted with a fresh target and store. The retry kept the
default directory absent. [Upstream logging settings](https://ninja.kunobi.com/docs/kache/getting-started/configuration)

A private mode-0700 cache is practical for avoiding accidental sharing.
Jobs running as the same Unix account still have the same file permissions.
A trust-domain label can route a cooperative job to a separate store. Use
separate build identities and OS-enforced write restrictions for distinct
trust domains. Compiler outputs include executable build scripts, proc
macros and tests. Shared writable cache contents therefore belong to the
same trust boundary as the code executed by a build. Shared hardlink restores
also share the inode with other targets when the option is enabled. Build
targets require their own paths even when the cache is shared. [Upstream configuration](https://ninja.kunobi.com/docs/kache/getting-started/configuration), [worktree guidance](https://ninja.kunobi.com/docs/kache/getting-started/worktrees), [project target isolation #542](https://git.kayg.org/kayg/infraternal/issues/542)

The existing opt-in sccache path has its own static reproducibility record.
This trial uses a wrapper-free control to isolate kache's effect, so a
measured improvement would still need a paired comparison with actual
sccache-enabled gates before a switch. [Existing compiler-cache record #329](https://git.kayg.org/kayg/infraternal/issues/329)

Path normalization, build-script replay and Cargo target seeding are
distinct mechanisms. An eligible Rust unit can restore from the store with
a fresh target. A build script can also restore files in `OUT_DIR` and the
directives Cargo would have heard. That second path depends on correct
`rerun-if-*` declarations and deserves independent verification because
the server build script generates the embedded migration list. Mainline target
seeding and incremental donor state are outside this trial.
[Upstream cache-key inputs](https://ninja.kunobi.com/docs/kache/how-it-works/cache-key),
[upstream build-script caching](https://ninja.kunobi.com/docs/kache/how-it-works/build-scripts)

## Nix package builds

`nix develop` supplies the interactive gate toolchain. The Cargo process it
starts reads the job environment and filesystem. The release package in
`nix/package.nix` is a separate derivation. It stages a vendored Cargo home and
target in its own build directory and builds offline. Compute01 reported
`sandbox = true`. A development-shell environment variable, private cache directory
and daemon socket are outside those declared inputs. This trial measures
Cargo under `nix develop` and leaves the sandboxed derivation unmeasured.
Nix store and binary substitute reuse remain available at the derivation
level. [Nix sandbox reference](https://nix.dev/manual/nix/latest/command-ref/conf-file.html#conf-sandbox)
