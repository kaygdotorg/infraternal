# VNC client libraries and end-to-end pipeline

**Issue:** kayg/infraternal#23

**Research snapshot:** 2026-10-06
**Scope:** browser → Rust relay → infraternal agent → RFB/VNC target. This is research only; no product library or engine is selected.

## Summary for the owner

There are three viable shapes to compare: forward RFB to a browser decoder; terminate RFB at the infraternal agent and forward a video stream; or terminate RFB in a Guacamole-style proxy and forward display operations. The RFB path is the only one that works against ordinary QEMU/Proxmox consoles without an agent-side decode/re-encode stage. QEMU's current RFB implementation supports common rectangle encodings and QEMU extended key events, but it does not advertise an H.264 RFB encoding, Fence, or ContinuousUpdates. [S8, S9, S15]

For a browser RFB implementation, noVNC has the broadest documented compatibility and is MPL-2.0-dominant. `vnc-rs` is permissively licensed and builds for WASM, but does not implement RRE/Hextile and lacks several common extensions. LibVNCClient and TigerVNC are broad native clients, but their GPL terms and native integration make them different choices from a browser-first library. Guacamole is an established decode-and-render proxy, but its VNC module uses LibVNCClient. KasmVNC has the most directly relevant built-in video modes, but its GPL-2.0 license and RFB incompatibility keep it as a reference, not a library candidate. [S1–S7]

The latest recorded host run is a bounded WebCodecs experiment, not a phone result: four H.264 decoder instances plus 2D canvas draws processed 720 1280×720 frames in 4.68 seconds (153.70 aggregate fps, 38.43 fps per pane). P95 submit-to-draw was 146.6 ms. One decoder processed 180 frames at 114.20 fps, with 50.9 ms P95. Three four-decoder runs ranged from 80.40 to 240.95 aggregate fps; only the latest run recorded load average (15.39 at start, 16.40 at end) on this 8-core host. Earlier runs did not capture load, so the cause of the spread is unknown. The browser was asked to prefer software decode, but WebCodecs does not expose which implementation was actually chosen; these results neither predict iPhone battery life nor establish a capacity target. [S13, S19]

## 1. Where to decode

| Pipeline | Latency and bandwidth | Phone CPU, battery, and quality | Complexity and failure modes |
|---|---|---|---|
| **A. Pass RFB to the browser**: relay RFB bytes; browser decodes rectangles with noVNC or a WASM engine. | One less decode/encode queue than transcoding. First frame still waits for RFB setup/authentication and the initial framebuffer. Bandwidth follows the server's selected RFB encoding and dirty rectangles: Tight/ZRLE can be lossless; Tight JPEG can reduce motion traffic with loss. Raw 1920×1080×32bpp at 60 full updates/s is a derived ceiling of about 3.98 Gbit/s before protocol overhead; real RFB sends changed rectangles and compressed encodings, so that is not a typical observed rate. [S1, S8, S15] | Text and terminal edges can remain pixel-exact in lossless modes. JPEG loses detail. The browser performs RFB parsing, decompression and canvas updates; four sessions may make this CPU- and memory-heavy, but there is no iPhone benchmark here. | Moderate. Needs an RFB-to-byte-stream adapter for our multiplexed transport and WebSocket transport/auth handling for endpoints like Proxmox. Risk is implementation variance in RFB auth/extensions and malformed-server input. The relay must preserve ordered bytes; WebSocket message boundaries are not RFB message boundaries. [S1, S8, S9] |
| **B. Decode RFB at the infraternal agent, encode H.264/HEVC/AV1, browser decodes with WebCodecs**. | Adds RFB decode, video encode, packetization, and usually a keyframe/GOP before the first usable image. On motion, bitrate can be controlled as video; there is no generic measured bitrate for this workload in the reviewed sources. QEMU/Proxmox requires agent-side decode/re-encode because its standard VNC server does not offer H.264 RFB. [S8, S9, S13] | Hardware decode can reduce browser CPU and often power, but the WebCodecs hardware preference is only a hint and can be ignored. Common 4:2:0 video can soften colored text; 4:4:4 preserves chroma better but must be supported end-to-end. H.264 is the most broadly established WebCodecs path in Safari; HEVC WebCodecs arrived in Safari 17.4, and AV1 WebCodecs in 17.5 only when an AV1 hardware decoder is available. [S13, S17] | Highest. Requires host capture/encode capability or software fallback, low-delay codec configuration, a new framed video protocol, resize/keyframe recovery, codec probing, and tests on real iPhones. Failures include no encoder on the host, unsupported profile on the phone, lost reference frames, extra encode delay, battery/thermal throttling, and poor text quality. Current Safari WebKit notes include a VideoDecoder H.264 frame-order fix in Safari 26.4, evidence that browser/codec combinations need device testing. [S10, S13] |
| **C. Guacamole model**: a `guacd` process decodes RFB and sends Guacamole display instructions and image data; the browser renders those operations. | Moves RFB parsing and framebuffer processing off the phone but does not turn VNC into a video codec. Guac 1.6.0 added a server-side update optimizer that detects movement and reuses/copies pixels, reducing repeated image data in supported cases. No comparable measured end-to-end number was found. [S6] | Browser draws custom canvas/image operations, so it avoids a full RFB decoder but still composites updates. It can preserve lossless RFB modes. Server-side CPU and copies rise; phone power savings are plausible but unmeasured. | High integration cost: extra daemon/protocol and placement where the VNC endpoint is reachable. Guacamole's VNC module uses LibVNCClient, so the VNC dependency/license boundary needs review. Failures include additional proxy state, resize/clipboard edge cases, and a second protocol implementation to maintain. [S6] |

`WebCodecs` is available in Safari starting with Safari 16.4 for video; HEVC support arrived in 17.4 and AV1 support in 17.5 on devices with a hardware AV1 decoder. Hardware acceleration is not assured by setting `hardwareAcceleration`; the specification defines it as a preference that user agents can ignore and says its power/performance trade-offs depend on the device and content size. Safari 26.4 also records a fix for out-of-order H.264 `VideoDecoder` output. Probe actual codec configurations and measure on target iPhones rather than infer from browser version alone. [S13]

- **noVNC H.264:** noVNC documents H.264 and has WebCodecs detection/decoder code. A proposed 2026 PR documents a failure mode where a dropped H.264 frame or decoder error could stall later reads; check current fix status if H.264 is selected. [S1]
- **vnc-rs Tight:** its README says Tight works; its example reports JPEG rectangles as JPEG events, which the renderer must draw. [S2]
- **vnc-rs resize:** current source documents ExtendedDesktopSize negotiation/events; its WASM build does not expose resize requests. [S2]
- **LibVNCClient TightPNG:** documentation lists TightPNG on the **server** side only, not its client. [S3]
- **LibVNCClient ContinuousUpdates:** the project says it is not supported. Fence implementation was not established in the reviewed client docs. [S3]
- **TigerVNC H.264:** the viewer includes an H.264 decoder path (libav); that does not imply a TigerVNC server can encode H.264. [S4]
- **Kasm H.264:** Kasm's 1.5 video stream is Kasm's video transport/mode, not interoperable H.264 RFB. [S7]

The noVNC compatibility edge is notable: README support does not guarantee every custom extension is bug-free under every browser. The reviewed issue list included H.264 hardware decode follow-up work and a ZRLE malformed-run CPU denial-of-service report. Any chosen parser needs a strict input-size policy, malformed-stream tests and fuzz coverage, matching decision D40. [S1, S3]

## 3. Servers the client will meet

| Server family | Practical compatibility bound |
|---|---|
| **QEMU / Proxmox VE** | QEMU source contains Raw, CopyRect, RRE/CoRRE, Hextile, Zlib, Tight, TRLE, ZRLE and ZYWRLE encoders plus QEMU extended key events, desktop resize and clipboard extensions. Current source does not define H.264 RFB, Fence or ContinuousUpdates. Proxmox's `vncproxy`/`vncwebsocket` path exposes the QEMU RFB session through the PVE HTTPS/WebSocket API and uses a console ticket; 2026 hardening binds tickets to the listener port and generates a fresh VNC password. Do not persist or log those tickets. [S8, S9] |
| **x11vnc** | Mirrors an existing X11 display and uses LibVNCServer. Expect standard rectangle encodings including Tight/JPEG and ZRLE, not a general H.264 RFB stream. LibVNCServer documents no ContinuousUpdates support. The x11vnc repository labels the project unmaintained and requests a maintainer, so it is a compatibility target rather than an implementation base. [S3] |
| **TigerVNC Xvnc / x0vncserver / w0vncserver** | Virtual X desktop and existing-display/Wayland capture tools are actively maintained. Expect traditional RFB encodings such as Tight/JPEG and ZRLE; TigerVNC's viewer has H.264 decode code, but reviewed sources do not establish H.264 encoding from its server. Upstream dropped official Windows server support in 2020. [S4] |
| **wayvnc + NeatVNC** | Wayland server for wlroots compositors only. NeatVNC's current release notes list H.264, extended clipboard, ContinuousUpdates and Fence support; H.264 depends on the GPU/encoder path (`wayvnc --gpu`) and the server's default capture cap is 30 fps. Issues show this path can fail when GPU/driver initialization is unavailable, so treat it as optional. [S10] |
| **macOS Screen Sharing / Apple Remote Desktop** | Apple documents VNC viewer access with a password when “VNC viewers may control screen with password” is enabled; Screen Sharing and Remote Management cannot both be on. Apple Remote Desktop has version-dependent native authentication/encryption and high-performance sharing behavior; this does not mean an arbitrary browser VNC client can use all ARD features. noVNC advertises Apple's older Diffie-Hellman auth, not all current ARD auth modes. Public Apple docs reviewed did not give a complete encoding table; negotiate and test against supported macOS versions. [S1, S11] |
| **Windows VNC servers** | There is no single Windows server matrix. TightVNC Windows Server added RRE and ZRLE and supports Tight/JPEG; UltraVNC and RealVNC add their own modes/authentication. Server versions/configuration vary, so request a safe common set and log negotiated features. TightVNC removed its ExtendedDesktopSize implementation in 2.8.81 due to incompatibility/complexity; do not assume all servers resize the same way. [S5, S12] |

The practical baseline is therefore server-negotiated RFB rectangles. H.264 can be enabled when both ends explicitly advertise it (for example, wayvnc with the required GPU path), not inferred from the fact that a browser can decode H.264. [S8, S10, S13]

## 4. Four or more panes in one tab

Suggested renderer experiments, not selected implementation:

- Keep each RFB parser/decoder off the main UI thread where possible. WebCodecs is available in Dedicated Workers, and Safari supports OffscreenCanvas 2D from 16.4, WebGL contexts in OffscreenCanvas from 17.0, and WebGPU starting in Safari 26.0. Treat WebGPU as an optional renderer path; keep a 2D canvas fallback. [S13, S14]
- Maintain one framebuffer surface per pane and apply RFB dirty rectangles in order. Batch presentation at `requestAnimationFrame`; if a pane is behind, avoid drawing stale intermediate surfaces once its latest complete state is available. Do not skip parsing stateful RFB messages. [S15]
- For standard demand-driven RFB, delay the next incremental framebuffer request for a hidden or small pane to reduce its update rate. If ContinuousUpdates is negotiated, explicitly disable it while throttled. Some common servers, including QEMU and LibVNCServer, do not implement that extension, so the client still needs request pacing. [S3, S8, S15]
- A 1920×1080 32-bit RGBA canvas is 8,294,400 bytes = 7.91 MiB; four base surfaces are 31.64 MiB. This is a calculated surface floor, excluding decoder surfaces, JS objects, GPU textures, compositor backbuffers and copies. The benchmark's 1280×720 surfaces were 3.52 MiB each and 14.06 MiB for four. [S19]

The host benchmark is useful only as a decode/draw sanity check. Its latest run kept four requested WebCodecs decoders above the 30 fps offline input rate at 38.43 output fps per decoder; p95 time from enqueue to draw was 146.6 ms. Observed four-decoder throughput varied across runs (80.40–240.95 aggregate fps); only the latest run captured host load, so the cause is unknown. It does not include capture, RFB parsing, RFB network, agent/server relay, phone GPU, cellular RTT, background-tab throttling, or battery. Use decision D41 scale budgets to set a phone test matrix before treating this as capacity evidence. [S19]

### Reproducible benchmark

Run from the repo root with Node.js, FFmpeg with `libx264`, and Chromium available. `CHROMIUM` can override the script's local Chromium path:

```sh
node research/vnc/benchmark/decode.mjs
```

Recorded 2026-10-06 on Debian 13, Linux 6.12.111, 8-core Intel Core i9-9900K @ 3.60 GHz, Chrome for Testing 153.0.8010.12, FFmpeg 9.0.1. The latest run started at 15:26:28 UTC and reported 1/5/15-minute OS load averages of 15.39/8.44/5.53 at start and 16.40/8.77/5.66 at end. The host had concurrent compilation activity; benchmark load was not controlled. Three observed four-decoder runs measured 80.40, 153.70 and 240.95 aggregate fps; load was captured only for the latest run, so do not infer a cause for the spread. The script generates 180 Annex-B H.264 Baseline 1280×720 frames (30 fps, six seconds), requests `hardwareAcceleration: "prefer-software"`, feeds one or four decoder instances without real-time pacing, draws every output frame with `OffscreenCanvas` 2D `drawImage`, and reports aggregate work, callback latency and load average. API preference is not proof of the selected implementation. The encoded test clip was 5,791,927 bytes (~7.72 Mbit/s for this synthetic clip); this is the benchmark input size, not VNC or cellular bandwidth. [S19]

## 5. Input, keyboard and clipboard

- **Keyboard:** QEMU ExtendedKeyEvent carries a physical scancode alongside the keysym, which is useful where the target layout differs from the browser layout. noVNC sends this when advertised and falls back to ordinary RFB keysyms. Keep composed text entry separate from physical key presses so iPhone's soft keyboard/IME is not forced through a one-keydown-per-character model. [S1, S8]
- **Pointer:** direct touch should map taps and gestures to absolute VNC pointer coordinates. A trackpad mode should send relative movement for precision panning; this avoids relying on desktop pointer-lock behavior on iOS. Kasm 1.5 adds relative mouse mode, and noVNC supports touch gestures, demonstrating both interaction patterns. [S1, S7]
- **Clipboard:** use ExtendedClipboard UTF-8 text when both peers support it. Classic RFB CutText is limited to Latin-1 in noVNC's fallback; noVNC replaces characters above U+00FF with `?`. Clipboard access from a browser is restricted to secure contexts and user activation; Safari also presents user-facing paste UI in some cases. Make paste/copy an explicit user action and offer a text field fallback. [S1, S15, S18]
- **Latency accounting:** measure key/touch dispatch → agent receipt → target input injection → next changed framebuffer/video output → browser present. A 60 fps display has a 16.7 ms frame interval; 30 fps has 33.3 ms. Those are cadence intervals, not an end-to-end latency target. The owner should set input-to-visible and first-frame targets against an agreed iPhone model and network RTT. [benchmark, S13]

## 6. Candidate architectures for the grill

These are candidates, not a recommendation.

| Candidate | Evidence / likely strengths | Risks that need measurement |
|---|---|---|
| **A. noVNC over the existing relay** | Existing browser implementation supports standard encodings, QEMU extended key, desktop resize, ContinuousUpdates and Fence. MPL-2.0 fits the stack's stated license list. Its raw channel adapter offers a starting point for our relay's framed byte stream. QEMU/Proxmox already expose RFB over the WebSocket proxy path. [S1, S8, S9] | Four-pane iPhone decode/draw CPU and battery; behavior with PVE ticket flow and Apple/Windows auth; current parser security and H.264 error handling. Need production screenshots and real-device measurements before UI integration. |
| **B. agent-side RFB decode → low-delay video → WebCodecs** | Directly targets motion bitrate and hardware phone decode. WayVNC/NeatVNC and Kasm demonstrate video-oriented paths; WebCodecs exists in Safari, but hardware selection and codec/profile availability must be probed. Host measurement above establishes only that Chromium's API path can decode four streams at desktop scale on this particular host. [S7, S10, S13, S19] | QEMU/Proxmox need re-encoding at the agent. No phone power or end-to-end number yet. New video transport, host encoder availability, codec profile/color fidelity and recovery logic all add foundational surface area. |
| **C. Guacamole-style RFB proxy protocol** | Mature proxy and browser client; server optimizer can improve copy/scroll update reuse. Apache project license is permissive, but VNC module uses LibVNCClient. [S3, S6] | Extra daemon/protocol placement, C dependency/license boundary, and browser compositing costs remain. No measured gain versus noVNC for the required 4-pane case. |

Sunshine/Moonlight is relevant as a video-streaming architecture reference: Sunshine is a GPL-3.0 host supporting GPU and software encode paths; a third-party browser Moonlight client uses WebCodecs/WebGPU. These speak the GameStream/Moonlight stream, not RFB, so they do not connect to an unmodified QEMU VNC endpoint. KasmVNC and Beam similarly show that browser video streaming is achievable, but do not establish an interoperable RFB client choice. The reported performance numbers from third-party streaming projects were not used as benchmark evidence here. [S7, S16]

## 7. Owner grill questions

1. **Which target devices and network conditions define D41 scale?** Pick iPhone generations/iOS baseline, one-pane vs four-pane layouts, Wi-Fi and cellular RTT/loss, and whether hidden panes must remain live. The decision changes how much weight to give a hardware video decoder.
2. **Which real servers are in S4's first compatibility set?** Proxmox/QEMU, Linux X11, Wayland/wlroots, macOS Screen Sharing and named Windows servers have different extensions/authentication and video paths.
3. **What product license boundary is acceptable?** noVNC is MPL-2.0-dominant; vnc-rs is MIT/Apache; LibVNCClient is GPL-2.0-or-later; TigerVNC is GPL-2.0; Guac's VNC path depends on LibVNCClient; KasmVNC is GPL-2.0; RealVNC is proprietary. Decide whether native linking, a separate process, or a commercial SDK is in scope after a dependency/license review.
4. **Is agent-side video encoding an expected host capability or an optimization only?** Generic QEMU/Proxmox VNC does not provide H.264 RFB. The video candidate therefore needs CPU fallback or a defined hardware requirement on every host.
5. **What is the minimum supported iOS/Safari version?** Video WebCodecs starts with Safari 16.4, while noVNC's published minimum is Safari 15. This materially affects whether video decode can be mandatory or optional.
6. **Which quality/input behavior is a product contract?** Specify whether text must remain lossless during motion, whether relative trackpad input is required, and whether clipboard sync must preserve arbitrary Unicode.

Decision D39 says a foundational engine choice comes back to the owner with measured trade-offs. This report deliberately leaves the architecture and library open.
