# BSD and appliance platforms for enterprise

Research for kayg/infraternal#71, recorded 2026-10-07. D20 currently lists FreeBSD on demand; D156 D4 asks this research to inform BSD and appliance priority. This ranks enterprise relevance and recommends paths; it does not change platform support policy.

## Recommendation

1. **Current TrueNAS (SCALE-derived Community and Enterprise): API integration first.** This is the strongest storage opportunity in the list. TrueNAS reports 500,000 active systems worldwide in 2025 and says more than 60% of Fortune 500 companies use the product, but it does not split those numbers by edition or publish an enterprise-only installed base. A vendor history also names a Prime Video NBA studio deployment. These are vendor claims, not an independent market census. The current API is a versioned JSON-RPC 2.0 WebSocket API, so an integration can collect documented product state without installing an infraternal agent; the facts and permissions available still need validation against each supported API version. [TrueNAS history](https://www.truenas.com/history/), [About TrueNAS](https://www.truenas.com/about-us/), [API reference](https://www.truenas.com/docs/scale/api/)

2. **FreeBSD general-purpose servers: the first BSD agent candidate.** The 2025 FreeBSD Foundation community survey received 2,127 substantially complete responses. Of the self-identified professional-user respondents, 65% primarily used FreeBSD on servers; 27% of all respondents said they primarily used FreeBSD professionally. Those are sample proportions, not population market share. The Foundation’s Netflix case study describes thousands of FreeBSD Open Connect servers and appliances, a credible large-scale deployment. Rust publishes Tier 2 targets with host tools for x86_64 and aarch64 FreeBSD. [2025 survey and methodology](https://freebsdfoundation.org/wp-content/uploads/2025/09/FreeBSD-2025-Community-Survey-Report-Final.pdf), [Netflix case study](https://freebsdfoundation.org/end-user-stories/netflix-case-study/), [Rust FreeBSD target](https://doc.rust-lang.org/rustc/platform-support/freebsd.html)

3. **pfSense Plus: a worthwhile firewall integration, through a supported management API.** Netgate claims more than 13 million pfSense installations and names US government agencies using pfSense Plus. These are vendor-reported totals and examples; they do not say how many installations are active or enterprise. Plus 25.07 and later includes Netgate Nexus, whose REST API and management interface target fleets of hundreds. First confirm the API is supported for an external read-only client. Do not install a general-purpose infraternal agent on the firewall as the default path. [pfSense Plus overview](https://www.netgate.com/pfsense-plus-software), [Netgate public-sector examples](https://www.netgate.com/blog/enhancing-cloud-security-and-networking-the-power-of-pfsense-plus-software), [Nexus documentation](https://docs.netgate.com/pfsense/en/latest/nexus/index.html)

4. **OPNsense: support the documented API; prefer observation over duplicating its manager.** No current public install-base or share figure was found in the project/vendor material reviewed. The core system has a REST API with per-user API credentials. OPNcentral, available in Business Edition, already gives a central inventory, resource and firewall status, configuration provisioning, and update view. The product’s native manager is evidence of enterprise use cases, not evidence of its size. [OPNsense API reference](https://docs.opnsense.org/development/api.html), [OPNsense API setup](https://docs.opnsense.org/development/how-tos/api.html), [OPNcentral](https://docs.opnsense.org/vendor/deciso/opncentral.html)

5. **pfSense CE: leave API coverage unresolved until there is a supported interface.** The Netgate installation total is not split by edition. CE has the documented console and optional SSH shell, but Netgate’s documentation says its planned RESTCONF API was not shipped. The default supported configuration interface is the web GUI and its configuration model; do not build a dependency on private GUI endpoints or shell edits. A normal SSH terminal can remain an explicit user connection where SSH is enabled. [pfSense SSH access](https://docs.netgate.com/pfsense/en/latest/recipes/ssh-access.html), [pfSense configuration file](https://docs.netgate.com/pfsense/en/latest/config/xml-configuration-file.html), [Netgate documentation PDF, API note](https://docs.netgate.com/manuals/pfsense/en/latest/the-pfsense-documentation.pdf)

6. **TrueNAS CORE: legacy compatibility only if customers still need it.** TrueNAS says CORE moved to maintenance-only in 2023; the CORE name was discontinued for future products as SCALE reached feature parity and became the current TrueNAS line. Its 13.3 release documentation is explicitly archived as end-of-life. CORE exposes its own API documentation, but this is a separate legacy API from current TrueNAS. Avoid making CORE the basis for a new agent or storage adapter. [TrueNAS history](https://www.truenas.com/history/), [CORE 13.3 API documentation](https://www.truenas.com/docs/core/13.3/api/)

7. **OpenBSD: niche, later, and only after a customer signal.** Its security and network-service design makes it a plausible firewall, router, and bastion host, but I found no reliable current enterprise install count or named large-scale deployment that supports a market estimate. OpenBSD’s PF is its own packet-filtering and NAT system, not an appliance management API. SSH and the host’s own tools are the management path. Rust’s OpenBSD targets are Tier 3. [OpenBSD PF guide](https://www.openbsd.org/faq/pf/index.html), [Rust OpenBSD target](https://doc.rust-lang.org/rustc/platform-support/openbsd.html)

8. **NetBSD: lowest priority.** No current enterprise install count, firewall/storage market-share estimate, or comparable large deployment surfaced in the sources reviewed. It can be administered through SSH and native tools, but the business case is weaker than FreeBSD’s. Rust has a Tier 2-with-host-tools x86_64 target; aarch64 and other targets are Tier 3. [Rust NetBSD target](https://doc.rust-lang.org/rustc/platform-support/netbsd.html)

The order reflects enterprise evidence, product fit, and engineering cost together. The ranks do not claim market share. If the owner weighs addressable footprint above direct agent usefulness, pfSense Plus can move ahead of FreeBSD; the evidence does not establish a precise difference in their enterprise populations.

## What infraternal users would expect

The expected surface differs between a server and an appliance:

- **FreeBSD, OpenBSD, and NetBSD servers:** an SSH terminal or installed infraternal agent terminal, identity and hardware inventory, OS and service health, and then (later) integration with the customer’s backup/configuration system. FreeBSD additionally offers ZFS and server/network roles that make pool and service health useful. The discovery matrix already identifies the OS-specific sniff and fact paths; use [research/discovery/REPORT.md](../discovery/REPORT.md) and [research/discovery/matrix.json](../discovery/matrix.json) rather than inferring an appliance from its FreeBSD base.
- **TrueNAS:** users will expect system and version inventory, pool/disk health, capacity, alerts, replication/snapshot job status, configuration backup state, and links to the existing TrueNAS management UI. Do not make infraternal the storage backup engine. The API version must be part of the adapter contract: TrueNAS 25.04 switched to versioned JSON-RPC over WebSocket and TrueNAS 26 removed the older REST API. [TrueNAS API reference](https://www.truenas.com/docs/scale/api/)
- **pfSense and OPNsense:** users will expect appliance/version inventory, interface and gateway state, CPU/memory/root-filesystem health, HA state, configuration history and backup status. A terminal is useful for break-glass diagnostics, but the firewall’s own GUI/API and console remain the supported management surface. Configuration or routing changes can sever the connection and are outside the initial read-only scope. pfSense has automatic encrypted config backups and local history; OPNsense documents protected backups, config history/diffs, and optional SFTP backups. [pfSense backup and recovery](https://docs.netgate.com/pfsense/en/latest/backup/index.html), [OPNsense backups](https://docs.opnsense.org/manual/backups.html), [OPNsense SFTP backups](https://docs.opnsense.org/manual/sftp-backup.html)

This follows the current decisions: D117 sizes the product for enterprise scale (including D124’s 500 terminal sessions and 50 remote-desktop sessions per server); D156 D4 leaves BSD/appliance priority to this research; D156 D8 supersedes the old D145 one-shot probe, so the current flow installs the infraternal agent before collecting host facts; and D156 D9 keeps early collection read-only. Appliance-specific API work fits that sequence better than installing a root daemon on network or storage appliances. (See [DECISIONS.md](../../DECISIONS.md).)

## Management interface and support boundary

| Platform | Supported/warranted management path | SSH and warranty/support implication |
| --- | --- | --- |
| FreeBSD / OpenBSD / NetBSD | Native OS APIs, system utilities, and SSH when the administrator enables it. No product API exists for the general OS. | A shell is a normal OS administration interface. There is no single BSD-project warranty rule for a shell login; any purchased OS or hardware support contract governs changes. |
| TrueNAS current | Use the documented versioned API for collection. Enterprise systems have support coverage; Community Edition has community/forum support. SSH is configurable, and TrueNAS recommends leaving it disabled and denying shell access unless needed. | A shell login is not, by itself, described as voiding warranty. The Enterprise EULA limits its software warranty for defects caused by non-TrueNAS modifications, and support excludes unsupported configurations. That is a reason to avoid installing an unapproved resident agent or editing the appliance outside documented APIs—not evidence that merely opening a shell voids coverage. [Support](https://www.truenas.com/support/), [SSH service docs](https://www.truenas.com/docs/scale/26/systemsettings/services/sshservicescreen/), [Enterprise support coverage](https://www.truenas.com/support/enterprise/), [Enterprise EULA](https://www.truenas.com/docs/scale/gettingstarted/useragreements/scaleeula/) |
| pfSense Plus | GUI/console for direct administration; Nexus is the first-party multi-instance REST API from Plus 25.07. | SSH is an official remote console/file-transfer option but disabled by default. Netgate says shell access for additional users is limited and warns not to manage SSH keys from the shell. Documentation does not say that SSH login itself voids warranty; unapproved persistent changes still need vendor support review. [SSH access](https://docs.netgate.com/pfsense/en/latest/recipes/ssh-access.html), [Nexus](https://docs.netgate.com/pfsense/en/latest/nexus/index.html) |
| pfSense CE | GUI/console and optional SSH. Netgate’s docs record that RESTCONF was planned but not shipped. | Do not depend on undocumented GUI calls as a stable API. Keep terminal access explicit and user-authorized; defer inventory/config API until a supported interface is established. |
| OPNsense | Core REST API with per-user key/secret and access-control privileges; OPNcentral is a Business Edition fleet manager. | SSH is a separately enabled service with configurable user/root and listener policy. Documentation does not claim shell access voids warranty; prefer documented API endpoints for a product integration. [API permissions and setup](https://docs.opnsense.org/development/how-tos/api.html), [SSH settings](https://docs.opnsense.org/manual/settingsmenu.html) |

**Answer to “does shell use void support or warranty?”:** not as a universal rule. The vendor documentation reviewed does not say that simply logging in over SSH voids the product warranty. It does define supported configuration mechanisms and excludes some unsupported modifications/configurations. The safe product rule to grill is: use official APIs for appliances, use SSH only for explicit interactive access, and do not install an infraternal agent on an appliance without the appliance vendor’s support position.

## Rust and infraternal-agent effort

| Target | Upstream Rust status | Implementation implication |
| --- | --- | --- |
| FreeBSD | x86_64 and aarch64 are Tier 2 with host tools. Rust documents current standard-library and libc support for currently supported FreeBSD releases. | A native FreeBSD agent is technically realistic on both common 64-bit architectures, but it is a separate target and BSD libc ABI from the existing Linux musl build. Add/test FreeBSD service installation and upgrade behavior; FreeBSD uses rc.d, which is not named in D18’s current systemd/openrc/runit/s6 list. [FreeBSD service documentation](https://docs.freebsd.org/en/books/handbook/config/) |
| NetBSD | x86_64 is Tier 2 with host tools; aarch64, armv7, and other listed targets are Tier 3. | A useful amd64 agent is feasible. ARM support brings Tier 3 maintenance and CI risk; the small enterprise evidence does not justify it first. |
| OpenBSD | OpenBSD targets are Tier 3, with no prebuilt Rust standard-library artifact from the Rust project. | Highest agent cost: maintain native build/test coverage and target-specific service/OS behavior. Keep API-free host facts and SSH limited until a customer requests it. |
| TrueNAS current | The current SCALE-derived product is Linux; Rust Linux targets can run technically. | Treat as an appliance API integration, not a generic Linux agent installation, per the discovery matrix and vendor support boundaries. |
| TrueNAS CORE, pfSense, OPNsense | FreeBSD-derived appliance images, but their APIs/configuration and update behavior differ from base FreeBSD. | Do not infer agent support from the FreeBSD target. Use product APIs where supported; require explicit vendor/customer validation before any agent build. |

Rust target tiers matter: Tier 2 CI guarantees that the target builds, not that its tests pass; Tier 1 guarantees both. None of these three BSD families is Tier 1 for the target architectures considered here. The libc crate has platform-specific FreeBSD, OpenBSD, and NetBSD interfaces, but crate availability does not replace our own target CI or appliance testing. Effort labels above are estimates; no BSD target build or appliance integration was benchmarked in this research. [Rust target-tier policy](https://doc.rust-lang.org/rustc/target-tier-policy.html), [FreeBSD targets](https://doc.rust-lang.org/rustc/platform-support/freebsd.html), [OpenBSD targets](https://doc.rust-lang.org/rustc/platform-support/openbsd.html), [NetBSD targets](https://doc.rust-lang.org/rustc/platform-support/netbsd.html), [libc crate](https://docs.rs/libc/latest/libc/)

## Owner grill questions

1. Should current TrueNAS Enterprise/Community API coverage be the first appliance integration after the Linux collector, or should the team first close the FreeBSD host-agent path?
2. For a FreeBSD agent, is x86_64-only the first cut, or should aarch64 ship at the same time? Both Rust targets are Tier 2, but each adds an OS build and real-host test lane. Who can supply a supported test host?
3. For pfSense Plus, is the public Nexus REST API supported for third-party read-only collection, or is Nexus only a human-operated management product? If the former, should it rank ahead of FreeBSD?
4. Should OPNsense integration attach to each firewall’s API or to an existing OPNcentral host? What read-only role/API permissions are suitable?
5. Is there a specific enterprise requirement for pfSense CE despite the lack of a documented first-party REST API? If yes, who will validate a stable supported surface?
6. Does any customer require TrueNAS CORE still in support, or is it an explicit legacy-only adapter after current TrueNAS?
7. Keep OpenBSD and NetBSD deferred absent an enterprise customer signal, or reserve a CI lane for one of them? OpenBSD has stronger network/security fit; NetBSD has a more mature x86_64 Rust tier.
8. Confirm the appliance boundary: API-backed observation first; do not install an infraternal agent unless the appliance vendor supports that deployment and the owner approves it. Defer configuration writes, firewall mutations, and backup ownership under D156 D9.

## Review checklist and limits

- All requested OS and product families are ranked separately where editions change support/API posture.
- Install numbers, survey rates, and named deployments are labelled as vendor-reported or survey-sample evidence; no unsupported market-share percentage is inferred.
- The technical mapping follows the discovery report and matrix. It distinguishes OS detection from appliance identity and does not infer agent support from a shared FreeBSD base.
- Support/warranty claims distinguish documented SSH capability from vendor-supported configuration and avoid saying shell login itself voids coverage.
- Rust tiers and libc status come from the Rust project documentation. Effort is qualitative, not a build/benchmark result.
- D117, D156 D8, and D156 D9 are applied; no decision, support contract, default, or API client was selected.
- No product code changed and no real BSD host or appliance was available for compatibility testing.
