# D348 pinned R4b method

This overlay pins each benchmark side to two CPUs on the 6-vCPU perf VM. The
current host has `isolcpus` configured and maps each vCPU to one host CPU. CPUs
1–2 belong to side A, CPUs 3–4 belong to side B, and CPUs 0 and 5 are reserved
for host services and housekeeping. This layout applies to every engine,
including kernel WireGuard and wireguard-go.
The harness, its audit sampler, and the `perf-run` launcher are also restricted
to CPUs 0 and 5, so they are not exempt from the runnable-task audit.

## Placement and restore

Inside the `perf-run` scope, the overlay reads each unit's `ControlGroup` and
captures `cpuset.cpus` and `cpuset.cpus.effective` from the matching cgroup.
It accepts the reboot baseline when `init.scope`, `system.slice`, and
`user.slice` either have configured `cpuset.cpus=0-5` or an empty configured
mask that inherits effective `0-5`. It captures those exact configured and
effective values, then pins the slices to 0–5's housekeeping subset, CPUs 0
and 5. Active host services inherit the system slice mask;
NetBird, Tailscale, containerd, Docker, and journald are checked from their
live cgroup masks. The configured `perf.slice` baseline is 1–3 and expands to
0–5 for the measured scope. Harness processes use CPU affinity 0,5; each
namespace-side child gets its exact 1–2 or 3–4 cpuset.

The global workqueue mask at
`/sys/devices/virtual/workqueue/cpumask` and every existing per-workqueue
`cpumask` are saved, set to hexadecimal `21` (CPUs 0 and 5), and restored.
Every virtio network IRQ is moved to housekeeping CPUs after its original
affinity is saved. The R4b namespace path uses veth, which has no device IRQ;
the audit records per-CPU `/proc/interrupts` and `/proc/softirqs` deltas to
show where IRQ and network softirq work lands.

The in-scope exit handler restores the saved service-slice masks, IRQ
affinities, and workqueue masks, then verifies those live values. It restores
`perf.slice`'s exact runtime drop-in files, `DropInPaths`, and `AllowedCPUs` in
that scope. The active `perf-run` transient scope can keep the parent
`perf.slice` cgroup mask widened until it exits, so the in-scope receipt records
that mask as pending instead of reporting a false restore failure. A second
locked `perf-run` reads the real cgroup files after the first scope has exited
and verifies the original `perf.slice` masks plus the saved file bytes and
metadata. The shared verifier accepts an explicit full guest mask in
`cpuset.cpus` where the saved value was empty only when the live effective mask
is still exactly `0-5`; it rejects any narrowed or expanded real mask. Empty
configured cgroup masks and empty drop-in lists use an explicit manifest
sentinel so tab-separated fields cannot shift during verification.
`AllowedCPUs` and `EffectiveCPUs` systemd properties are recorded for context;
the cgroup files and exact drop-in snapshot are the source of truth for
restoration.

## Matched kernel row and link offloads

The counted kernel comparison uses `kernel-plain`: the case creates `wgA` and
`wgB` with `ip link add ... type wireguard`, configures them with `wg set`, and
sets both tunnel MTUs to 1420. It has no NetBird process or setup path. The
older NetBird kernel row used `wt0` at MTU 1280 and remains a separately labeled
historical reference. Each NetBird row took 174–178 seconds in the last hold,
so the pair is not repeated in a cut hold.

Each row records `ethtool -k` for both tunnel interfaces and the `a0`/`b0` veth
underlay interfaces. `offloads/offloads.json` records each link's MTU and
whether the reported GSO and GRO feature groups have enabled features; the raw
`ethtool -k` and `ip -o link` outputs remain beside it. `version.json` records
the engine's configured userspace UDP GSO/GRO path where that metadata is
known. The `ethtool` flags describe interface configuration, not packet
counts, so reports do not claim that an enabled feature processed a specific
number of packets.

Each loaded-window audit samples the per-CPU steal field from `/proc/stat`.
The JSONL samples retain the tick values; each `summary.json` reports the
window delta by CPU, test-CPU seconds, housekeeping-CPU seconds, and the
percentage of test-CPU time lost to steal. This lets the owner compare the
two perf-VM placements without mixing steal from separate windows.

## Interference audit

The audit samples `/proc/<pid>/status` and `/proc/<pid>/schedstat` once per
second while both sides run. It records `State`, `Cpus_allowed`, the current
CPU, cumulative runtime, and cumulative scheduler run delay. A runnable
non-kernel task whose allowed CPU list intersects CPUs 1–4 rejects the window.
Every process in the two test scopes
must also have exactly its side's expected `Cpus_allowed_list`.

Bound kernel workers are classified only when all of these match: the task is
a child of PID 2 (`kthreadd`), its cgroup is `/`, its name is `kworker/N:*` or
`ksoftirqd/N`, and its `Cpus_allowed_list` is exactly the single CPU N. The
audit sums each worker's `/proc/<pid>/schedstat` runtime delta by CPU and role,
and reports both those subtotals and the total over the loaded window.
`ksoftirqd/N` is classified as network softirq workload. In the kernel-NetBird
case, `kworker/N:*wg-crypt-wt0` is classified as WireGuard crypto workload.
These workers perform the measured network or crypto workload for their row:
their schedstat deltas are reported by worker, CPU, role, and total, but they do
not use the unrelated-background budget. The audit sums only matching workers
classified as `background` and rejects a window when that unrelated runtime
exceeds 0.5% of the four test CPUs' wall-clock time; exactly 0.5% is allowed.
Any non-kernel runnable task allowed on a test CPU remains a hard failure.
Other root kernel tasks are reported separately.
The perf utility and `/proc/sched_debug` are not available on this VM. The
per-task `schedstat` run-delay deltas and sampled runnable states are therefore
the run-queue evidence for this setup; the report records that limitation.
Validation's LAN throughput window is 10 seconds, matching counted windows, so
a short smoke interval does not let one brief bound-worker burst dominate the
0.5% unrelated-work budget. Other validation probes keep their smoke counts.

## Three-control calibration

Calibration runs the same fork binary three times as `control-a`, `control-b`,
and `control-c`, with 3,600 LAN probes per flow count. The script checks the
raw ping footer to confirm that each flow actually sent the expected probes (8,000 by default, #260). It
calculates p50 from received replies and loss-aware p99 by adding one infinite
sample for every missing reply before ranking the raw RTTs.

The loaded fixed-count ping uses `-c <count>` (8,000 by default) without iputils' overall `-w`
deadline. With `-w`, iputils waits for the requested number of replies and
can transmit additional probes after loss, so that flag would invalidate an
exact sent-probe count.

The load window must outlast the probe stream: the 72 s default load covers
8,000 probes at 5.5-8.1 ms each. `cases/mesh.sh` fails the window when the
probes are still running as the load ends, because idle round trips would
bias the loaded p99 low. `perf-all.sh --ab` runs one ABBA round (control,
candidate, candidate, control) of these windows in a single hold.

For each metric, the reported repeat spread is `(maximum / minimum - 1) × 100`;
the control is the metric-wise median of the three rows. The published
unpinned same-control history sets these pass limits:

| Metric | 1 flow | 8 flows |
|---|---:|---:|
| Throughput max/min spread | 1.6% | 0.8% |
| Loss-aware p99 max/min spread | 3.2% | 5.9% |

The overlay reports p50 and CPU-seconds/Gbit spreads too. No unpinned limits
for those metrics were published with the same-control history, so they are
reported but do not change the calibration pass. Pinned values are compared
only with pinned values; unpinned history remains a separate reference.

A failed audit, incomplete raw probe set, or spread above a published limit
fails calibration and normally keeps candidate holds disabled. A passing
calibration is the prerequisite for counterbalanced candidate holds.

The owner may explicitly direct a counted hold to proceed after a failed
calibration. Such a hold keeps its own result and evidence, but the calibration
remains failed; every report must state the failed spread and label the hold
owner-directed. For this matrix the exact row label is
`uncalibrated, owner-directed`; show measured and owner-reported spreads beside
the label. Do not combine those pinned results with unpinned history or
describe the calibration as passing.

## Source-aware engine matrix

Each scenario uses five shared-lock measurement windows. Each window contains
one row for plain kernel WireGuard, one for wireguard-go, and one for each
GotaTun source variant. This matrix contains the shipped baseline, J88i, J316,
J225, and J324, so each window has seven rows and each source receives five
repetitions. Later candidates join the same window contract with their full
source SHA recorded in the row and table.

The default counterbalanced order rotates the seven-engine row order by one
position per window:

| Window | Row order |
|---|---|
| 1 | plain kernel WireGuard, wireguard-go, GotaTun shipped 84b7bb2, J88i fairness 33ca6fe, J316 b678934, J225+J316 21a8a15, J324 b36d575 |
| 2 | wireguard-go, GotaTun shipped 84b7bb2, J88i fairness 33ca6fe, J316 b678934, J225+J316 21a8a15, J324 b36d575, plain kernel WireGuard |
| 3 | GotaTun shipped 84b7bb2, J88i fairness 33ca6fe, J316 b678934, J225+J316 21a8a15, J324 b36d575, plain kernel WireGuard, wireguard-go |
| 4 | J88i fairness 33ca6fe, J316 b678934, J225+J316 21a8a15, J324 b36d575, plain kernel WireGuard, wireguard-go, GotaTun shipped 84b7bb2 |
| 5 | J316 b678934, J225+J316 21a8a15, J324 b36d575, plain kernel WireGuard, wireguard-go, GotaTun shipped 84b7bb2, J88i fairness 33ca6fe |

J324 memory pools, wireguard-go, kernel, then rotates each later window.
Pass `--select-gotatun` for the selected GotaTun rows plus `--engine-order`
for every measured engine ID to `matrix.py run`.

Every row uses MTU 1420, side A CPUs 1–2, side B CPUs 3–4, housekeeping CPUs
0 and 5, the same `h2h` probes, and the same placement audit. No engine gets
its own sysctl or benchmark-only feature setting. Link offloads are recorded
for each row. Keepalive is disabled for all three WireGuard implementations.
After setting the scenario's network profile, every row completes the same
first-packet warmup before its idle CPU sample. Idle CPU sums selected engine
process threads (or the kernel WireGuard crypto workers) with test-CPU
`ksoftirqd` threads; the helper rejects a row when it cannot see the engine's
process or crypto workers.

The scenario IDs and probe workloads are:

| Scenario | Workload |
|---|---|
| `best-lan` | LAN, one and eight TCP flows, 3,600 paced UDP RTT probes with a 1,392-byte payload (1,420-byte inner IPv4 packet). |
| `wan-50ms` | 25 ms one-way delay and 5 ms jitter on each direction; same TCP and MTU-size latency probes. |
| `wan-150ms-loss-0.5` | 75 ms one-way delay, 15 ms jitter, and independent 0.5% loss in each direction. |
| `wan-150ms-loss-2` | 75 ms one-way delay, 15 ms jitter, and independent 2% loss in each direction. |
| `wan-20ms-loss-1` | 10 ms one-way delay with 5 ms jitter and independent 1% loss in each direction. |
| `small-udp` | 100,000 unpaced 64-byte and 256-byte UDP payload probes, with separate idle and loaded loss-aware RTT samples. |
| `peer-scale` | 1, 100, and 1,000 peers on each endpoint, keeping one peer active for one-flow TCP throughput and loaded RTT at every scale. |
| `handshake-storm` | 30 sequential forced peer removals and re-additions, each followed by a first-reply probe; the reported interval starts before the reset and therefore includes reset/configuration plus handshake time. |
| `cpu-contended` | The LAN workload with one busy loop pinned only to housekeeping CPU 5. |
| `idle` | Warm tunnel idle CPU and MTU-size plus 64/256-byte RTT probes; peer memory at 1, 100, and 1,000. |

Each per-row JSON retains throughput, sent/received/lost counts, p50/p99/p99.9
loss-aware RTT, CPU seconds/Gbit, idle CPU seconds/minute, idle process RSS at
each peer count, kernel peer-memory evidence, binary size and allocated disk
blocks, syscalls/Gbit, and artifact hashes. Userspace RSS is read from
`/proc/<pid>/status` `VmRSS`, and PSS from `/proc/<pid>/smaps_rollup` `Pss`.
Both sum the same selected endpoint process trees for every userspace engine;
the raw status and `smaps_rollup` files are retained beside each row JSON.
Peer-scale rows also retain loaded
RSS and kernel-memory samples while the same one-flow TCP and latency probes
run. Loss-aware percentiles rank over all sent
probes; a rank reached only by missing replies is represented as null and
listed in `infinite_at`. Kernel memory uses the `wg_peer` `/proc/slabinfo`
delta when present. Otherwise the row identifies the system-wide
`/proc/meminfo` Slab delta, which is not peer-attributed. Userspace engines
report kernel peer memory as not applicable.
Every idle peer-count sample uses the same configured quiet interval after
that count is installed (15 seconds in a counted run) before RSS and kernel
memory are read. The loaded sample is taken one second into the five-second
peer-scale TCP transfer, while the same latency probe runs. Other scenario
tables keep their loaded peer-count fields null because they do not run this
memory-specific workload.

TCP CPU/Gbit comes from the whole-machine `/proc/stat` delta during the TCP
transfer window. Small-UDP CPU/Gbit uses the same whole-machine busy-jiffy
counter around the complete probe command, divided by received payload Gbit;
the JSON retains the CPU window and transferred-byte denominator. UDP packet
rate remains based on the sender window, and loss is reported separately.

`lib/matrix.py run` writes one machine-readable run JSON, one JSON and Markdown
table per scenario, row-level JSON, audit and cleanup evidence, and raw logs.
The table aggregates only rows whose `perf-all` cleanup status is zero. A row
without a status record remains failed or missing, and unavailable counters
remain null instead of becoming zero.
