# Owner build-option question for static key memory, #154.

Source cause confirmed: pinned openssl-src 300.6.1+3.6.3/src/lib.rs:631-634 adds -DOPENSSL_NO_SECURE_MEMORY to every musl Configure command. crypto/mem_sec.c:109-127 consequently returns 0 without attempting mlock or madvise. Production 8cff05cd and branch b0cf61ef pin identical provider versions. Increasing memlock or changing systemd sandboxing cannot enable code removed by compilation.

The brief explicitly requires an owner decision before a different OpenSSL build option. Candidate: remove the musl-only disable define while keeping the existing pinned OpenSSL and Zig, then add a self-check of the production static executable that requires return 1, resident locked pages and dump exclusion under 8MiB. Alternatives: patch openssl-src itself (explicit but fork upkeep), narrowly remove the define in the pinned compiler wrapper (small but compiler-policy coupling), or add a separately built OpenSSL (duplicates build ownership; not recommended). No replacement crypto engine is proposed.

Measurements are attached in the final evidence report. No build-policy repair or dependency change is applied until the owner selects how the existing provider is built. Root fail-closed remains unchanged. The new runtime regression will intentionally fail on today's static binary; it must land with the selected repair, rather than weaken startup enforcement.

Root/systemd measurements on infraternal-perf-test (Linux 6.12.69+deb13-amd64), shared lock held, load 0.00/0.00/0.00 -> 0.08/0.02/0.01:
- Baseline static provider: init_return=0, VmLck 0->0 KiB, refused at LimitMEMLOCK=8388608, infinity and unit default. No key allocations or other locked memory precede initialization in the reproducer.
- Candidate (only mem_sec.c enabled, original pinned archive otherwise unchanged): init_return=1, VmLck 0->1024 KiB under all three limits; all 10,000 synthetic 32-byte allocations are secure and resident in lo/dd mappings. 320000 bytes used; 0 after freeing. 1MiB heap per server, independent of host/session count; 10,000 retained keys consume 320000 secure bytes.
- Static x86 diagnostic size 3873384 -> 3881736 bytes (+8352). This is the provider diagnostic delta, not a measured whole-server repair delta. Production code is unchanged (0-byte source-induced delta); final server size and latency must be measured after the build policy is chosen.
- Candidate mem_sec.c compiles without extra Linux headers using checksum-pinned Zig 0.15.2. Removing the old disable define is feasible with this sysroot. No new dependency is required by this candidate.

Owner question: should this repository narrowly remove the upstream musl disable define in its pinned musl compiler wrapper, or maintain an explicit openssl-src patch? Both enable the existing secure heap; choose the build ownership before the production change. Recommendation: narrow wrapper handling of the exact upstream define for the two pinned Linux/musl targets, documented and covered by the final executable self-check. Reject increasing memlock: unlimited still returns 0. Reject replacing the allocator: the existing provider protects real pages once compiled in.

Blocked for owner build-option choice as expressly required by this brief; repair/regression not claimed complete. Evidence: evidence/ca-static-heap/root-systemd.txt, probe-build-x86.txt, heap_probe.c and build_probe.py. Fast gate was invoked before handoff; its final state is recorded in the finish note.
