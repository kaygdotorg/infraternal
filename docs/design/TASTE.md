# TASTE.md: the owner's design taste, written down

<!-- SPDX-License-Identifier: AGPL-3.0-only -->

This file shapes every piece of UI in infraternal, whoever builds it: the
orchestrator, a fork, or a future design agent. Read it before you touch UI,
and check your work against it before anyone else sees it.

Each rule comes from something the owner actually spotted. The quote is
there so the reason is never lost. **When the owner spots a new annoyance,
add it here the same day**, with the quote, the rule and how to check it.
Never delete a rule. If the owner changes their mind, mark the rule
superseded and say why.

Related decisions: D72 (overlay material), D158–D162 (windows, gestures,
one component per concept, mockup rounds), D171 (Claude builds the UI).
Related documents: `segmented-selection.md` and `toast.md` in this folder.

---

## 1. Restraint ("did being subtle die?")

| Rule | Owner said | Check |
|---|---|---|
| **No rings from mouse, touch or shortcuts.** Focus rings show only during real Tab navigation. They come from the shared helper `packages/ui/src/focus-ring.ts` (`data-focus-ring="on"`), never from bare `:focus` or `:focus-visible`. | "every checkbox has automatic selection rings on checking them?", "no selection rings for mouse actions, no automatic selection rings for keyboard shortcuts" | Click every control: no ring. Open with ⌘K: no ring. Press Escape: no ring. Press Tab: a ring. |
| **Selection is quiet.** A ticked checkbox changes only the checkbox. A selected list row may get a faint tinted fill, but never a border or an outline. | "a selection border shows up everytime i tick something?" | Tick rows and look for borders, outlines or glows. |
| **No fake glass.** No glossy bevels, inner highlights or thick borders on in-page controls (buttons, capsules, segmented controls, close buttons). Glass is only for floating overlays: palette, popovers, tooltips, sheets (D72, D160). | "there's a fake glass spectacle?", "the fake glass highlight is still there" | Zoom into every in-page control at 2×: flat fill and at most a 1 px hairline. |
| **No settings inside a flow.** A flow does one job. Configuration (sources, extended info, toggles) lives in Settings, if it exists at all. | "why is 'discovery sources' even a thing?" | List every toggle in a flow and justify each one, or move it out. |
| **One input, not modes.** No tabs to switch between "discovered" and "manual". One field filters, and anything it doesn't recognise becomes the manual path. | "there is no reason for there to be two tabs when there is an input field already?", "anytime the user types something that is not recognized, assume it's a manual flow?" | Count the mode switches. The target is zero. |
| **No invented chrome.** No counters, labels, headers or badges that the decisions don't call for. | "it looks nothing like our existing product's aesthetics", "generic slop" | Every element maps to a decision or to the flow's job. |

## 2. Consistency with the product

| Rule | Owner said | Check |
|---|---|---|
| **Match the existing look exactly.** The deployed core screen, sign-in card and palette are the reference for radii, borders, button styles and sizes, spacing and type. Extend `packages/ui`; never restyle a component locally (D160). | "please, please, please make sure it matches our existing aesthetic" | Put a capture next to the sign-in card and the core screen; nothing may look foreign. |
| **Mockups are built inside the product**, behind a flag, against the mock test double, never as standalone pages. | "I only want mock-ups that actually look like our product" | It runs in `apps/tracer` with `?proto=`. |
| **Monospace everywhere.** The UI font is Geist Mono. Hierarchy comes from weight and size, never from a second family. | "the next mockup you draw, let that be monospace font everywhere (different weight where it applies of course)" | Grep for sans fonts. Never capture with `?ui=sans`. |
| **Typography must match the sign-in card exactly.** Same font size, line height, letter-spacing, weight and colour for the same role, and the same density and spacing between lines. Copy the sign-in card's computed values per role; do not approximate. Mono looks good only with the right tracking and leading. | "I don't know the text alignment/density/weight/maybe even how close the text is. it doesn't feel right. looks nowhere close to the sign in page monospace text where i was like damn this looks good." | Diff the computed `font-size`, `line-height`, `letter-spacing`, `font-weight` and `color` of the title, lede, body and labels against the sign-in card: identical. Compare 2× crops side by side. |
| **Weights:** body 450, names and labels 500, titles 600, secondary text 400 in `--fg-2`. Match the sign-in card role for role. | "I think the font weights can be improved" | Compare computed weights with the sign-in card. |
| **One type scale everywhere (D174).** Text sizes follow the sign-in card on every platform; touch devices get bigger targets (44 px) through padding and row height, not bigger text. Toasts and tooltips use the same tokens. *(Superseded: a separate 16/15/13 px touch text scale.)* | "make sure we use the same size text for desktop… the toast looks weird for sure" | Collect the computed font sizes across the product: only scale values. |
| **Platform-sized controls.** Desktop follows the macOS scale: icon buttons about 28 px, rows 28–32 px, sidebar rows about 28 px. Touch follows iOS: 44 px targets. | "the close button is ridiculously big on desktop?", "too much vertical space on the sidebar items?" | Measure the controls at 1440×900 and at 393×852. |
| **Alignment on a 4 px grid**, with one shared left edge for title, input, list and buttons. Nothing touches anything without spacing. | "fonts alignment and sizing is completely fucked up", "proper alignment" | Look at 2× crops of the edges. |
| **Text sizes follow Apple's guidelines.** Phone values are 15–16 px or larger, keys 13–14 px or larger. Contrast is at least 4.5:1, measured over the real background. | "text too small" | Computed sizes plus a pixel-measured contrast check. |
| **Enough icons.** OS marks for hosts, small status icons instead of bare coloured dots, and icons in headers, failures, consent and progress. 16 px on desktop and 18 px on touch, with a 1.5 stroke. | "it still feels too raw! there's not enough icons" | Each row and state has an icon where a native app would have one. |

| **Icons over text for actions.** Where an icon is unambiguous (close, confirm, cancel, copy, share, add, settings), use an icon button with the shared warm tooltip naming the action, rather than a text button. Text buttons remain for primary flow steps whose meaning an icon can't carry (for example "Continue"). Every icon-only control has a tooltip and an accessible label. | "prefer icons over text please, icons with warm tooltips" | No icon without a tooltip. No text button where an obvious icon exists. |
| ~~Desktop pills are generous.~~ **Tried and dropped (2026-10-08):** the owner compared larger desktop pills (46 px, 16–17 px labels) and kept the current size. | "our current size looks better anyways so let's throw that idea out" | — |

## 3. Motion

| Rule | Owner said | Check |
|---|---|---|
| **Every state change animates.** Continue, Back, mode changes and success use a short slide plus crossfade (about 200 ms, `cubic-bezier(0.23,1,0.32,1)`), in the direction of travel and interruptible. Reduced motion falls back to opacity only. Keyboard-opened overlays (⌘K) stay instant. | "continue has no animation, back has no animation, changing manual → discovered has no animation" | Sample frames during each transition. |
| **Step transitions are fluid, not jarring.** Continue and Back use one shared step-transition component with spring physics: the card height springs to the new content while the old step slides out and the new one slides in, no snaps, no abrupt fill flips. Reuse the sign-in card's pane transition (which the owner likes) instead of a new one. | "the continue or back animation is no longer motion/fluid/springy, it is jarring" | Record Continue and Back at 60 fps and step through the frames: continuous position, opacity and height; no frame where content jumps or the card height snaps. |
| **No lag while animating.** Every frame stays under 16 ms. No per-element colour transitions on theme switches: at most one opacity crossfade. | "theme changing could also be way smoother? it's now lagging as it animates" | Record a performance trace of the switch and look at frame times. |
| **Popovers grow from their trigger**, with `transform-origin` at the anchor. | (Apple guidelines and Emil audit, round 3) | Look at the mid-animation frame. |
| **Splits are playful physics.** Splitting a window divides it like a water droplet: the outlines genuinely fuse and stretch, stay joined by a thinning liquid neck, snap apart with overshoot and wobble to rest (a metaball/goo effect on silhouettes; text is never filtered). Merging reverses it with surface tension. The UI is meant to be fun to use, so structural changes get character, not a plain slide. | "the splitting should be very bubbly btw, like a water droplet splitting into two. bouncy, sticky and springy. we make the UI fun to use!", "it should be adhesive… think of it also like the dynamic island… what we have right now is a very amateur attempt" | Record a split frame by frame: visible neck, overshoot and settle; reduced motion crossfades. |
| **Work is instant; animation never gets in the way.** Every operation finishes its work at once (≤ 16 ms, no long task); animation only presents an already-finished result. (1) Input is never blocked: keys, clicks and taps work from the first frame, even mid-animation. (2) Results and content you are waiting to read (search results, filtering, terminal output) appear instantly, never animated in. (3) Repeated keyboard actions (arrowing through lists, typing, rapid window stepping) don't animate. (4) Opening and closing surfaces may animate even from the keyboard, briefly: about 180 ms when key-triggered, up to about 300 ms from pointer or touch; always interruptible, and the same key reverses it from where it is. | "every operation in the app is blazing instant fast and it's the animations that take time", "keyboard-driven actions generally should not animate only when that slows down the user… animating the results appearing in the search palette would be bad UX… I don't think animations should ever get in the way of the user" (replaces the earlier blanket "keyboard actions don't animate") | Measure work per operation; type immediately after ⌘K and check the first character lands; results update without motion; arrow keys move instantly. |

## 4. Layout and behaviour

| Rule | Owner said | Check |
|---|---|---|
| **A flow is its own floating card over the window it belongs to.** The window behind it dims, and the flow card is lifted with a real shadow so it clearly floats. It is centred in that window, and on success the same window becomes the result (D-rule above). | "the wizard should be its own floating card while dimming out the terminal, the wizard should feel floating, lifted with shadows" | Capture the flow over a busy terminal: the terminal is dimmed, the card has elevation, and no second window opens. |
| **Flows live inside a window card**, centred both ways. On success the same window becomes the result. Never open a second window beside the flow. | "the wizard should be within a terminal window only… start the middle (both vertically and horizontally) of a terminal card" | Run the flow from start to success: one window throughout. |
| **Nothing moves without a reason.** A window moves on a sidebar toggle only if it would be covered. | "why does the add host wizard move when sidebar is opened or closed when there's more than enough space?" | Toggle the sidebar with a window open in the centre: no movement. |
| **The sidebar toggle lives in its own pill and travels with the sidebar.** When the sidebar is open, the toggle sits in a pill at the top right *inside* the floating sidebar (like the macOS 26 sidebars). When it is closed, the same pill sits at the top left of the UI. The move is one smooth, shared-element animation, never a jump. The pill and the window card are each one shared component, reused everywhere (D160). | "the sidebar could have the sidebar button in the sidebar itself rather than sticking out?… when the sidebar is open, it stays on the top right in a pill… stays at the top left of the ui when sidebar is closed. animate it, make it smooth. polish." | Toggle the sidebar and sample frames: the pill glides between the two positions, and no second toggle exists. Grep for one-off pill or window styles. |
| **The floating sidebar is real glass:** the shared overlay material (translucent, with a visible blur of what is behind it), with no bright top-edge highlight. | "sidebar still does not have proper transparency/blur?" | Capture the open sidebar over a busy terminal and the canvas background: content shows through, blurred. |
| **No layout jumps on selection.** Choosing an option (a radio card, an expanding field) animates its height and fill; nothing below it jumps. | "selecting one or the other checkbox there results in a jarring shift, not animated" | Record frames while switching options: continuous heights, no one-frame jumps. |
| **Multi-entry fields use chips.** When typed text matches something (a discovered host, or a valid `user@host`), it becomes a pill-shaped chip inside the field, and you keep typing without a comma. Backspace on an empty field edits the last chip. One shared chip-input component. | "I should be able to add multiple hosts like this… once something matches, it should become a chip (pill-shaped) of its own in the input field while allowing me to type more without me having to hit comma" | Type three hosts in a row with no commas; each becomes a chip; Backspace walks back. |
| **Batch actions show every item.** Adding many hosts at once shows each host's own progress and result. Nothing is silently dropped, and the result opens every host. | "when I selected multiple hosts to be provisioned, I still saw only one got added… I would love to see how adding 10 hosts at once would look like" | Run the flow with 10 hosts: 10 progress rows, 10 results, 10 windows. |
| **Confirmations are small and native-feeling.** An anchored confirmation is a compact popover: a short title in the body size and weight 500, one secondary line if needed, and two compact **icon buttons**, right-aligned: × to cancel and ✓ to confirm (about 28 px on desktop, 44 px targets on touch). Each has a warm tooltip that names the action ("Cancel", "Install as root"), and the same name as its accessible label. ✓ uses the product's primary style; × is quiet. No oversized pills, no theme-coloured slabs, no ring on open. *(Superseded wording: text buttons with verbs. The owner prefers icons with tooltips.)* | "this is a total abomination though, both in yes no sized pills and the text and the overall aesthetic"; "prefer icons over text please, icons with warm tooltips over plain text like that so in this case it would be x and a tick" | Capture at 2×: two icon buttons, no text buttons. Hover each and see a warm tooltip with the action name. No rings. |
| **Floating cards are clearly translucent, with one shared material.** The machine popover, the add-host card, confirmation popovers (such as "Install as root?") and every floating card use the same overlay material: content behind is visibly present, softly blurred, neither near-opaque nor so blurred it reads as solid. Tune it once in packages/ui; never per card. | "info card needs to be more transparent (either is too opaque or too blurry right now). add hosts card should also be way more transparent? code reuse, please?", "that \"install as root...\" popover card also needs to be the part of the same translucent card thing" | Capture each floating card over a busy terminal: identical material, content behind recognisable. |
| **Overlays stay inside the window they belong to.** A popover or flow card never extends beyond its window card. Its maximum height is the window's inner height minus the same inset on every side, so the layout stays symmetric. | "I would love a bit more symmetry… the info card slightly extends beyond the terminal card at the maximum height? I would love it if it were inside the terminal card instead" | At 393×852 and 1440×900, the overlay's box is inside the window's box with equal insets. |
| **Lists breathe at the end.** Scrolling lists in cards keep the same bottom padding as their top, so the last item never touches the edge. | "the last item in add 3 hosts card is too close to the bottom end" | Scroll to the end: bottom padding equals top padding. |
| **No rogue notifications.** Every transient message uses the shared toast in its standard place. Nothing toast-like appears in a corner on its own, and test-double errors never surface as UI. | "there's also a \"Request could not be completed\" thing that appears at the bottom left of the mockup? it's a toast but not a toast?" | Click through every flow and watch the corners: only the shared toast ever appears. |
| **Windows resize directly.** On desktop, drag any window edge or corner, with a proper resize cursor. On touch, a deliberate press-and-hold gesture reveals resize handles. Mobile gestures must be intuitive and discoverable; they get their own design round. | "terminal windows should be easily resizable with mouse cursor on desktop and with a tap-hold thing on mobile maybe? we need to think about really nice, intuitive visual gestures to do things on mobile" | Resize by edge and by corner on desktop; press and hold on touch, then drag a handle. |
| **Status is an icon with motion, not a text box.** Connection states (connected, slow, reconnecting, resumed with an approximate screen, offline) show as a small, pretty icon with motion for each state, plus a warm tooltip that explains the state in words. Never a bordered text line in a corner. | "this shit appears in production too? this should be a pretty icon with motion somewhere with nice icons for each state and warm tooltips that describe the state" | Drop and restore the connection: no text box ever appears; the icon changes state with motion; hover or long-press shows the tooltip. |
| **Nothing modal that doesn't have to be.** On desktop the sidebar docks and never blocks the page. | "if the sidebar is open i can't click on anything?" | Open the sidebar and click every visible control (`elementFromPoint`). |
| **Everything fits the visual viewport and the safe areas.** Header and actions stay pinned, the middle scrolls, and nothing sits under the status bar, notch, Dynamic Island, Safari's bottom bar, the keyboard tray or the home indicator (`env(safe-area-inset-*)` with `viewport-fit=cover`; visual viewport, never `100vh`). Backgrounds still run edge to edge. | (rounds 4–5, footer over the key tray); "You also did not account for the Safari top and bottom safe areas, which are very important." | Phone captures with the content scrolled to the end. |
| **Copy without buttons.** No copy icons next to text: double-tap copies on touch, one click copies on desktop, and an inline tick plus "Copied" confirms it. Keys and values copy separately. | "why is there a copy to clipboard button everywhere?", "the fields key and value should be individually clickable to copy" | Click a key and a value separately; each copies its own text. |
| **Key/value rows:** keys left-aligned, values right-aligned. A long value wraps, still right-aligned. Never an ellipsis. | "make keys left aligned and values right aligned" | Long values at 320 px wide. |
| **No redundant overview chrome.** The canvas is the overview, so there is no strip of every open host at the top. | "there is no reason to show all the open hosts at the top? i can just horizontally scroll the canvas" | The top bar holds only the current session capsule and `+`. |
| **Canvas gestures:** tap activates a window without opening the keyboard, one finger scrolls the terminal, two fingers pan the canvas, pinch changes the font size, and a desktop trackpad pans horizontally anywhere (D159). | "I can't seem to activate a card by directly tapping on it", "horizontally scroll the canvas (which does not work right now btw)" | Touch tests via CDP, plus wheel tests over a terminal and over a gap. |
| **`?` shows shortcuts in place.** Pressing `?` morphs the top-middle pill into an expanded shortcuts list. Shortcuts for the current area come first, then the global ones; every future area (containers, LXC, Kubernetes) brings its own section. No separate help page or modal. | "we need a ? shortcut in the UI that just morphs the pill (top middle pill) into an expanded shortcuts list with the current area shortcuts first" | Press `?` in the terminal and on the canvas: the pill morphs open, the current area is listed first, and Escape morphs it back. |
| **Cards hug their content.** A card is exactly as tall as what is in it, with bottom padding equal to the top; no leftover space under the last action. | "the black card is still longer than necessary (vertically)" | Capture every pane: the gap under the last control equals the top padding. |
| **Light and dark everywhere, colourful app defaults.** Every screen, including sign-in, has a light and a dark version that follows the system. Sign-in stays monochrome; the app's default themes are coloured, never the mono pair. | "we also need to have a light version of the sign in page too", "let's not use mono themes as default btw. they're too boring (in the app i mean, not the sign in page)" | Load with system light and dark and no saved theme: the sign-in matches, the app opens in a coloured theme. |
| **Move windows by their pill, into structure.** Hovering a window's pill shows a grab cursor; dragging it lifts the window and moves it left, right, up or down. Windows always land in the tiling structure (columns and rows); never free-floating or overlapping. | "hovering over this pill should turn the cursor into dragging so I can drag terminals up/left/right… make sure we have this structured and not entirely free-form like overlapping terminals, etc. that would be a mess to maintain" | Drag a window by its pill in every direction: the others reflow, it snaps into a slot, and no two windows ever overlap. |
| **Every tap answers.** Anything tappable gives immediate feedback (a press scale, and for copy the inline tick plus "Copied"). Nothing is inert. | "tapping on the commit id has no feedback" | Tap every control on touch and click it on desktop: each one visibly responds. |
| **Version lives in About, not in chrome.** The version and commit are shown only in Settings → About, which ⌘K "About" also opens. The sidebar footer is only the signed-in person and Settings, and it must not look plain. | "the design looks boring kinda here. I don't think version number belongs here. only in the settings overlay… cmd + k > about / version should also open that" | No version text anywhere in the sidebar; ⌘K "about" or "version" opens About. |
| **One behaviour, one component, everywhere.** A copy gesture, a tab switch or a press looks and moves the same on every screen, because every screen uses the same shared component (copy feedback from the sign-in card, the gliding capsule tabs). A screen that re-implements one is a bug, even if it looks close. | "this tab switching logic is no longer using the animation… tapping keys or values in the info popover has no subtle copy animation like in the sign in screen? can we focus on code-resue and consistency please?" | Grep for local copies of shared behaviours; tap a value in every popover and switch every tab set: identical motion. |
| **Window chrome sits on the frame.** Controls that belong to a window (the lock) float on its frame line: the control's top edge is aligned with the frame's top border, never floating loose inside or above it, and never moving: the lock stays at the exact top centre whatever the title length, hover, resize or font load. Labels are short and literal ("Lock input"). | "the lock button randomly shifts to the left top or right top", "the lock should in the floating on top of the window frame with the top line of the lock square aligned to the window frame. just say \"Lock Input\" instead" | 2× crop of the window top: the lock's top edge sits on the frame line. |
| **Tapping empty canvas focuses the canvas.** A tap or click outside every window clears the active window: no window keeps its highlight border, and keys go to canvas navigation. | "tapping outside a window should focus on the canvas and should no longer have the terminal window frame highlight border" | Click a gap between windows: no accent border remains anywhere. |
| **Highlights hug their content.** A hover or selection highlight on a value sizes to the text with small even padding, never to the row or cell. | "the hover / selection state is wider than the text? it should be contain the text." | Hover a short right-aligned value: the highlight starts just before the first character. |
| **Every state change moves, even when you're fast.** Status lines, notices and panes transition (crossfade, icon morph), never swap. A click during an entrance animation still plays the next transition from wherever the motion is. | "there's no animation between these two states", "If I press continue with recovery on page load too fast, i don't get the motion animation" | Type and paste into validated fields; click the next action at 0, 50 and 150 ms after load. |
| **Errors sit by the action and reveal nothing secret.** A failure appears directly above the primary button, animated in. Validation of secret input (recovery words) says how many items are recognised, never which one is wrong. | "I feel like we shouldn't tell the user which word is incorrect?" (and the failure line rendered below "Back to sign in") | Enter a wrong word: only a count is shown; force a failure: the message appears above the button. |
| **Feedback never depends on success paths you can't see.** The copy animation plays on the gesture on every origin (a fallback copy when the async clipboard is unavailable). The cursor over copyable text is a pointer, never the "+" copy cursor. | "why does the cursor change to the + icon and there is still no copy animation?" | Copy from a plain-http LAN origin: the tick plays and the cursor is a pointer. |
| **One click does the whole intent.** Clicking a control on an unfocused window (the lock) focuses the window and performs the action in one go. | "if the window is not focused and I click on the lock icon, it does nothing but focus the window while it should do both in one go?" | Click the lock of an inactive window once: it becomes active and locked. |
| **Containers hug their content.** Pills and rows (the profile pill, palette selection) size to their content plus padding; a selection highlight leaves even gaps to neighbouring headers. | "the profile pill does not need to be so wide", "the selection highlight is too long? it is almost touching the section header" | Measure the gaps above and below a selected palette row; the profile pill ends after the name's padding. |
| **New concepts are built on the existing app, never beside it.** A mockup of a new idea reuses the product's real chrome (windows, pills, top pill, sidebar, palette, material, type) so approving it cannot pull the look elsewhere; only layout and motion are new. | "I like all the animations… but it does not follow our app aesthetics… if I approve this, it's going to result in a derailment" | Put the mockup's captures next to the current preview's: same borders, radii, type, material, pills. |
| **Structured freeform: snapped by default.** Selecting a view or flying to something lands snapped: windows framed, swipes and scrolls move window to window (horizontal between columns, vertical within a column) with a spring, no zoom and no resting between windows. A toolbar snap toggle frees the canvas; switching views turns snap back on. | "whenever I select a view, whenever something flies in, I expect it to be snapped… There should be a snap button in the toolbar… that should automatically turn on as I switch between views… too free form… on mobile" | On a phone: swipe in all four directions lands on whole windows; pinch does nothing while snapped. |
| **No stray bands or scaffolding bars.** Nothing draws a full-width band at the screen edges; review scaffolding stays small and in a corner. | "I see a bottom band for some reason. please remove that" | Phone captures: the canvas meets the toolbar and screen edges cleanly. |
| **The palette is centred and sized by its results.** On desktop ⌘K opens centred in the viewport, not anchored to the top pill. It grows and shrinks vertically, in both directions from the centre, with the number of results, up to a quarter of the viewport from the top and from the bottom. Its width stays fixed for now (wider layouts are reserved for future rich previews). | "the search palette should appear centered on desktop rather than appearing right next to the pill. And it should grow in both directions until it reaches one fourth from both the top… and the bottom… very dynamic… grow and shrink according to the number of results" | Type a query that narrows from many results to one: the palette stays centred and its height follows the results, between the cap and its minimum. |
| **The canvas is dotted and the dots travel with it.** The background (theme gradient, mesh or a picture) shows through an even dot grid that moves exactly with the windows when panning and flying, and thins out when zoomed far out, so moving through the canvas feels physical. | "Can we have a dotted canvas background instead?… any picture or any gradient, but dotted so that moving through it, I think it's a very nice effect" | Pan and fly: dots move 1:1 with windows; at 40% zoom the grid is calm, not noisy; frame time unchanged. |
| **Closing re-tiles.** Closing a window reflows the structure: the remaining windows in its column grow to fill it, an emptied column disappears and its neighbours close the gap, with the layout spring. | "they don't automatically tile back after one window is closed… I close the bottom one, the top one doesn't extend to the bottom" | Close the top and the bottom of a two-window column, and the last window of a column: no gaps remain. |
| **Swipes follow the finger.** Anything dragged or swiped moves in the same direction as the finger, 1:1 until release. | "the bar swipe is inverted. If I swipe up, it swipes down" | Touch-drag every swipeable surface up, down, left and right. |
| **Error and empty states get the same rhythm as the happy path.** An error card uses the same spacing, brand mark and button style as the screen it replaces: the gap between the message and its action equals the sign-in card's, never cramped. | "the button is too close to the text? why did it slip from your UI audit?" | Capture every error, offline, expired and loading state; measure the text-to-action gap against the sign-in card. |
| **Toolbar rows snap.** Switching the mobile toolbar's rows is a snap, never a free scroll: swipe up snaps to the first row, swipe down to the second, following the finger while dragging and never resting between rows. | "It's a freeform scroll right now, which looks very weird… swipe up should be a scroll snap to the first row, and swipe down… to the second row" | Swipe up and down with short and long drags: it always lands on a whole row. |
| **Window header actions live in one pill, on every device.** A window's top-right actions (split right, split down, close) sit together in one pill, the same height as the title pill; on phones the same pill adapts (44 px hit targets through padding, the title truncates first). Redundancy with the toolbar and ⌘K is intended. | "put them in a pill, like a toolbar pill… rather than have them float alone", "window header actions pill should be on mobile too, redundancy is good. we can adapt!" | Desktop and phone: the action pill aligns with the title pill; touch targets ≥ 44 px. |
| **The keyboard opens only for a real text field.** On phones, the on-screen keyboard appears only when a real input has focus (a focused terminal, the palette field, a rename). Toolbar buttons never take focus or summon the keyboard; the **key row exists only while a terminal has input focus**; without one, the toolbar shows only the canvas row, with no second row and no dots. | "tapping any key on the canvas row spawns the keyboard? same for the keyboard row even though there's nothing to focus?", "if there's no use for the key row when navigating the canvas, we can even hide that row… our app should be intuitive" | Tap every toolbar control with nothing focused: no keyboard, no editable element focused. |
| **The camera keeps things where they belong.** A lone window stays centred after every event (open, close, resize, reload, sidebar, font or theme change). The sidebar is a layer above the canvas: opening or closing it never resizes the canvas or moves the camera or any window, wherever the windows are; only the sidebar itself slides. ## 6. Process (how taste gets enforced)

- **Only the orchestrator builds UI** (D171). Codex jobs never design or restyle UI.
- **Nothing reaches the owner unverified.** Click through every state in a real browser at 1440×900, 393×852 and 375×667, in the ink and paper themes, including the unhappy ones: errors, offline, expired, empty and loading states, not only the happy path. Read every screenshot, and check this file row by row. A passing test suite is not proof of taste.
- **Mockups come before product** (D162). No new UI ships without mockup rounds and the owner's approval.
- **When the owner spots something, write it here first, then fix it.**
